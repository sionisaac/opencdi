# BIOS/core validation: initial baseline

These developer tools use locally supplied ROMs and discs. They contain no
commercial firmware, extracted modules, proprietary disassembly or copied shell
assets. They do not modify the user's ROMs, settings, NVRAM or running app.

## Tools

Build:

```text
cargo build --release --bin bios_audit --bin bios_contract --bin harness
```

`bios_audit <rom>...` prints input identities and an OS-9/68000 module inventory:
file offsets, sizes, names, types, editions, SHA-1 and CRC status. Known system ROMs
are normalized to CPU word order through the existing BIOS identifier. Unknown
byte orders are not guessed. Header parity, in-image bounds, bounded printable
names and the 24-bit module CRC are checked. A missing inventory or bad module CRC
returns a failing exit code. This does not validate all boot code, uncovered bytes,
module authenticity or runtime behavior. Offsets are not runtime addresses.

`bios_contract <cdi220b.rom>` boots a disposable machine for 700 fields, snapshots
it and runs 18 F$CRC inputs through TRAP #0, service $17, in both precise stepping
and the 32-cycle batching path used by the machine (36 checks). Every case
restores the snapshot, places an original six-byte caller and synthetic data in
scratch RAM, and checks return, carry and the low 24 bits of D1 against a portable
polynomial implementation. Inputs include empty buffers, zero/FF, a familiar
numeric string, all byte values and 4096 generated bytes, with three initial CRCs.
The probe currently admits only the identified 220 F2 ROM. It uses supervisor calls
with interrupts masked; it does not test user-state
dispatch, scheduling, device timing or another CPU implementation. Never run this
scratch caller against a live user's emulation session.

`harness` now shares the app's handover predicate and uses its repeated shell click
sequence. Mono-IV does not receive Mono-I shell clicks. `--require-launch` rejects
a run with no detected handover, including a zero-frame negative control. Handover
is still a shell heuristic, not proof that gameplay is ready. The app's existing
predicate is unchanged. Saved-state replay and immediate resave mismatches now
produce a nonzero exit code; previously replay could report DIFFER while passing.

Run the scoped baseline with Python 3:

```text
python tools/validate_bios.py --bios-dir "path/to/bios" --disc-dir "path/to/discs" --output "path/to/new-results"
```

The current fixture expects cdi220b.rom, cdi490a.rom, vmpega.rom, impega.rom and the
user's exact filenames for 3rd Degree (USA), Mad Dog McCree (USA, Europe), and Chaos
Control (USA), with .chd extensions. File identities, per-case logs, trace summaries
and results.json go only to the selected output directory. Trace files contain
register/memory observations: keep those local rather than bundling them in a
public firmware replacement. OS-9 error returns can be normal feature probes.

Unit/app checks, avoiding unrelated old standalone diagnostic binaries:

```text
cargo test --lib --bin harness --bin bios_audit --bin bios_contract --bin opencdi
```

The specification tests in `src/spec_tests.rs` check valid ADPCM range expansion,
the four documented predictor gains with integral history vectors, and signed
saturation, using the May 1994 specification IV.4.3/IV.5.3. They intentionally make
no claim about fractional rounding, invalid parameters, a complete audio stream
or hardware conformance.

unmapped writes. These need board-specific investigation. Repeatability does not
establish a working 490 player or justify changing the core based on guesses.

## REA and further investigation

REA's raw-binary provider documents big-endian m68k analysis, but its Windows
Ghidra boundary explicitly excludes m68k. No REA installation or agent configuration
was changed for this baseline. Next, use a supported host/provider or a reviewed
adapter; describe ROM mapping and real entry points explicitly. REA's raw loader
maps file offset zero at the supplied entry and does not infer reset vectors or
CD-i memory maps. A whole ROM begins with vectors/data, not necessarily executable
code at byte zero. Preserve file identity and distinguish ROM offsets, mappings,
relocated code and guessed function boundaries.

Primary tool references:

- https://github.com/morluto/rea/blob/main/docs/providers/raw-binary.md
- https://github.com/morluto/rea/blob/main/docs/providers/windows-ghidra-p0.md
- https://github.com/morluto/rea/blob/main/LICENSE

Priorities: extend observable syscall contracts (memory/modules, pointer status,
disc reads and errors); capture interrupt/sector/video timing; compare failures to
the specification and real-hardware observations; then add minimal regressions and
fix confirmed core discrepancies. Running the original BIOS inside OpenCDi is not
an independent hardware oracle. No new core defect is confirmed by this baseline.

A redistributable replacement BIOS remains a separate, substantial implementation
project. Keep behavioral requirements, evidence and original implementation
provenance separate. Do not translate recovered proprietary code or reuse its UI
assets and assume the tool's licence covers them. The supplied specification has
rights/confidentiality notices; distribution review remains necessary. This work
creates validation infrastructure and an original CRC helper, not a replacement
BIOS, clean-room certification, or a guarantee of redistribution rights.

## Follow-up: pointer and real disc-read contracts

Build the additional `bios_io_contract` and `disc_data_audit` binaries. Run:

```text
cargo build --release --bin harness --bin bios_io_contract --bin disc_data_audit
python tools/validate_bios_io.py --bios "path/to/cdi220b.rom" --dvc "path/to/vmpega.rom" --disc "path/to/3rd Degree (USA).chd" --output "path/to/io-results"
```

`bios_io_contract` runs 32 pointer observations/error checks against the original
220 BIOS: PAL/NTSC, movement, edges, buttons and release, origin, repositioning,
motion after repositioning, invalid handles and closed handles. It executes a
scratch TRAP caller in a disposable machine while the normal machine runner advances
device time. The shell can leave a mode-specific origin, so tests set an explicit
origin. This BIOS scales slave Y to 480 lines in NTSC; a raw 560-line coordinate
must not be asserted unchanged. These are synthetic API checks, not physical gun
or Wiimote testing. SS_PT selector values are scoped to the identified firmware.

With `CDI_OS9_TRACE` and optional `CDI_IO_HASHES=1`, successful I$Read return buffers
now include a bounded SHA-1 observation. No read occurs on a failed service;
requests beyond one MiB, impossible counts, overflowing or unmapped buffers are
refused. The observer uses side-effect-free peeks and changes no guest state.
Regular tracing remains unchanged unless the additional flag is set.

The normal 1300-field Third Degree boot returned four buffers matching the image:
the volume descriptor and the entire loader, attract and bumper modules. The
comparison uses hashes, not exported file bytes. Two other observed I$Read calls
were NVRAM/settings reads and are outside this disc comparison. Hashing on/off
produced identical video/audio signatures. The fixed fixture deliberately fails if
any of these four expected results is absent; it is not an all-file coverage claim.

`disc_data_audit` independently walks the bounded root directory of a CD-i/ISO
volume and hashes contiguous Form-1 root files up to one MiB. Interleaved, Form-2,
large and unreadable files are skipped and counted. It is a test oracle for this
small fixture, not a general disc extraction utility. Both paths still use OpenCDi's
container reader, so they are independent above the sector transport, not an
independent CHD implementation or hardware oracle.

This work confirmed and fixed a host disc-metadata defect: album/publisher were
read from publisher/preparer offsets, and metadata was read from unnormalised raw
sectors at a fixed Mode-2 payload offset. The corrected reader handles known cooked
payloads, Mode 1/Mode 2 Form 1, byte-swapped and scrambled sector forms, checks
descriptor identity and reads the proper fields. The raw controller API is unchanged.
Synthetic regression fixtures cover both modes and all swap/scramble combinations,
cooked descriptors, bridge detection, invalid headers and rejection of Form-2/audio.
This is a metadata/type-detection fix, not a demonstrated gameplay or boot-speed fix.

The earlier Mono-IV accesses were located in ROM modules: CIAP 7000 in `ciapdriv`
at offset 0x23e, I2C access in `hobdriv` at offset 0x25c, and the unmapped writes in
`kernel` at offsets 0x2e7c/0x2e86. Module attribution narrows the investigation but
does not establish the intended register semantics. No guessed CIAP/I2C behavior
has been added.

Early injected filesystem-read experiments did not establish a valid end-to-end
file-read contract; those prototypes are kept outside the repository. The retained
disc test observes successful calls during normal BIOS/game execution instead.
At that stage seek/EOF/error injection was not yet validated. The following stage
covers selected cases; interleaved streaming, hardware timing and a replacement
BIOS remain further work.

## Follow-up: file position, EOF and error contracts

```text
cargo build --release --bin bios_file_contract --bin disc_data_audit
python tools/validate_bios_files.py --bios "path/to/cdi220b.rom" --dvc "path/to/vmpega.rom" --disc "path/to/3rd Degree (USA).chd" --output "path/to/file-results"
```

The new disposable probe boots normally until CPU execution is inside the loaded
Third Degree application module in user state. It then substitutes an original
TRAP caller, preserving the real process and its stack. Scratch code/parameters
use the emulator's separate system RAM window, rather than overwriting application
modules in video RAM. It never resumes this modified game as a user's session and
never loads/saves the user's persistent NVRAM. This is an emulator-specific test
fixture, not a standalone diagnostic that can run on physical hardware.

The earlier idle-process injection experiments lacked the initialized application
filesystem context. Their failures were not evidence of a device emulation defect.
Using the actual application context permits normal absolute-path file operations.

The suite passes 46 service/comparison checks in each of PAL and NTSC (92 total):
open/size/position, sequential reads, forward/backward seek, odd offsets, crossing
a 2048-byte sector boundary, partial reads at file end, EOF status and read errors,
read-only write rejection, close/closed-handle use, missing files and invalid handles.
Read buffers have untouched guards beyond the requested extent; EOF does not alter
the supplied data byte. The fixture is deliberately limited to the known 69-byte
root text file and 30720-byte loader of this disc. Expected sizes are explicit.

Seven returned data ranges per video mode (14 comparisons) match independent
payload-reader hashes. `disc_data_audit --contract-slices` supplies bounded slice
hashes without exporting file bytes. The runner requires all seven comparisons
and all 46 probe checks for each mode, and checks BIOS/DVC/disc SHA-256 identities
again afterward. All three input files remain unchanged.

One manual/firmware discrepancy is retained as an observation, not concealed as
a passed specification assertion. VII.2.2.3.1 says the non-EOF query returns D1=0.
For the identified 220 BIOS, its CDFM routine internally produces zero, but the
kernel restores the saved caller D1 (the service selector, 6) on successful return.
At EOF, carry and E$EOF are returned correctly. Precise instruction stepping and
the normal cycle-batched machine runner agree in both modes. The precise probe
also checks the final register restoration against the value actually stored on
the caller stack; it is not just a comparison of two execution paths. No special
core override was added to force a different register value.

These results support the specific contracts above, not complete BIOS/CPU accuracy.
They do not cover all permission modes, directories, corrupted media, interleaved
streams, seek latency, scheduling fairness or every firmware revision. Source bytes
still come through the shared CHD reader. No game-compatibility improvement or new
emulation fix was established in this stage, so the existing app build remains
current; the changes are developer probes, reference slices and documentation.

## Follow-up: interleaved audio selection and asynchronous abort

This stage confirms and fixes a Mono-I CDIC routing defect. CPU sector selection
checked the file number, but the audio-selection helper did not. During a Mode-2
read, a foreign file's ADPCM sector could therefore bypass the failed file check,
reach the decoder, modify transfer RAM and raise a sector-ready interrupt when its
audio channel happened to be selected. The new check requires the file register to
match before an audio sector is eligible. Independent CPU/audio channel masks are
otherwise unchanged.

The synthetic regression failed before the fix: one foreign sector reached the
decoder when the expected count was zero. With the fix, foreign file/EOF sectors
are ignored, a masked audio channel stays quiet, and a correctly selected sector
still decodes and raises its interrupt. Additional controller tests check cancel
and restart with a new file/location, selected EOF delivery exactly once, and
equivalence of large/small host tick chunks across alternating file numbers in
PAL/NTSC. These are original synthetic sectors and audio groups, not game data.

The selected-file requirement follows VII.2.2.3.2 / SS_Play in the supplied
specification, including the file-selection condition on VII-43. MAME's CDIC
implementation also rejects an unselected file before considering audio routing:
https://github.com/mamedev/mame/blob/master/src/mame/philips/cdicdic.cpp
Its device model is itself partial, so this is corroboration, not hardware proof.
The implementation and tests here were written locally; no source was copied.

`bios_file_contract ... --stream [--ntsc]` adds asynchronous BIOS tests from the
same disposable application context. It opens `bumper.rtf`, builds an original PCB,
selects all channels with audio 0/15 routed to the AP, and ignores other payloads
through null CIL pointers. Observed selectors for this identified firmware are
SS_Play 0x2d and SS_Abort 0x31. The suite checks start, progress, rejection of a
second play or synchronous read on the busy path, abort Done/Error and E$Abort,
stopped position/decoder progress, rewind/restart/reabort, close and invalid handle.
Both PAL and NTSC pass 21 checks each (42 total). Signals are disabled; synchronous
abort from another process is not covered. Linked CIL/PCL completion is tested
separately below.

The file validation runner now includes those two streaming cases, in addition to
the earlier 92 file checks and 14 byte-range hash comparisons. Input ROM/disc hashes
remain unchanged. This stage also reruns the boot/saved-state baselines and scoped
library/app tests before preparing a separate test build. First-sector/seek latency,
physical audio timing, real Wiimote input and all-game compatibility remain outside
these checks. No particular commercial title has yet been shown to depend on the
foreign-file defect; the regression demonstrates the incorrect core behavior.

### Reproducing gameplay after handover

The headless harness accepts `--post-input <script|@file>` to run pointer/pad
events relative to the detected disc-program handover. This implies autoplay and
requires a successful handover. `--input` retains its absolute-frame meaning;
the two options cannot be combined. Saved-state replay restores the handover
frame and input player as well as the machine.

`--nvram-in <file>` seeds a disposable machine from exactly 8192 bytes. The
harness disables NVRAM persistence, so guest writes never change the input file
or a default save file. `--nvram-out` remains an explicit optional export.
For reproduction with personal saves, use a working copy of the save file.

### The 7th Guest: first-room investigation

The USA game disc with the identified 220/VMPEG pair reproduces an event-queue
overflow after reaching the staircase. Audio driver notifications with value
0xC010 repeat during DMA rearming. The game dumps its queue and then dereferences
an invalid hotspot address (observed 0x00CFC35C). Fresh-NVRAM full-intro runs and
copied personal-NVRAM skipped-intro runs both reach this failure; PAL also fails.

FMA command PLAY ARM previously raised the decoding-started interrupt immediately
on every arm, including DMA rearming. The specification's MA signal/event mask
describes DEC as "Decoder started decoding" (IX-170). The model now raises that
notification when the first audio frame actually decodes, once per decoder reset,
on both timestamped and untimed paths. Original synthetic tests check the first
notification and ensure repeated arms cannot generate additional start events.

A separate UART defect obscured the game's diagnostic output: command and clock
register offsets were conflated, command writes were also emitted as data, and
the shared machine interrupt selector omitted UART TX. Register mapping and the
TX interrupt route are corrected. The serial sink remains immediate; physical
baud timing, incoming serial data and modem handshaking are not implemented.
Register layout corroboration: https://github.com/mamedev/mame/blob/master/src/devices/machine/scc68070.cpp
No implementation code or firmware bytes were copied.

The extra UART mode/clock state changes the saved-state format to version 12.
Version 11 snapshots are rejected explicitly; per-disc NVRAM saves are unchanged.
`CDI_BUS_FAULT_TRACE=1` enables opt-in bus-fault and CPU-exception diagnostics;
it is not enabled during ordinary play. Local test results and reproduction
limitations are recorded separately from claims of full-game compatibility.

### Extended playback and linked-buffer transfers

The user confirmed that the separate 7th Guest test build fixes the reported
first-room failure in live play. Further isolated tests cover Mad Dog McCree
NTSC intro/menu playback and Chaos Control PAL menu/attract playback through
12,000 fields, replaying fields 7,000–12,000 from a saved state. Picture and audio
match exactly on replay. A 9,000-field 7th Guest PAL run uses scripted D-pad/button
input to move from the staircase to the doors and replays fields 5,500–9,000
exactly. This is not full-game completion or physical-controller automation.

Synthetic audio tests also verify that stop/restart allows a fresh start signal,
separate audio keeps decoding after video program-end, temporary underflow does
not terminate the audio item, and a shared multiplexed program-end finishes both
streams. These checks add no production behavior changes.

`bios_file_contract ... --buffers [--ntsc]` extends the real application-context
tests to non-null video CIL/PCL lists. A bounded, independent root-directory
lookup locates `bumper.rtf`; the first two video sectors on one channel are
compared with the BIOS-delivered payloads. Two one-sector PCLs are linked, with
separate sentinel-filled buffers and signals disabled. Checks cover full/error
flags, submode/coding metadata, byte offsets, exact payloads, untouched guards,
CIL advancement through both buffers, abort completion, stable buffers after
abort, and close. PAL and NTSC each pass 14 checks (28 total); both deliver the
same two 2324-byte payload hashes. The validation runner includes these cases and
checks input-image hashes before and after. This does not yet cover circular
lists, overrun recovery, buffer-full signals or corrupt-sector error maps.

### Identified 490 / IMPEG validation

The earlier no-launch result was a missing automated player-menu click, not
proof that the cartridge or disc loader failed. An explicit Play click launches
The 7th Guest. The shared frontend/harness boot helper now waits for initial
CIAP reads to finish and IKAT pointer reports to be enabled, then clicks the
490 player's Play CD-i button. The sequence completes its release even when
launching makes the drive busy. Readiness uses serialized drive state, not a
diagnostic sector counter. The existing 220 sequence remains unchanged.

The 490 pointer contracts exposed truncation of absolute 10-bit IKAT positions:
host (1,1) became BIOS (0,0). Absolute reports now round upward into the requested
pixel; the BIOS performs its own NTSC Y scaling. Relative reports remain relative
so PT_Pos cursor repositioning still works. Both PAL and NTSC pass 16 checks
each, including buttons, edges, origin, repositioning and following movement.

Saved-state replay also exposed an omitted IKAT `reported` position. After a
load, later relative movement used the speculative future position. The field
is now serialized; a regression fails before the fix and passes afterward.
This changes the current saved-state format to **13**. Earlier format 11/12
snapshots are rejected; in-game saves and NVRAM formats are unchanged.

`bios_contract` now accepts the identified 490 as well as the 220 and passes the
same 36 F$CRC cases. `bios_490_contract bios impeg Third-Degree-disc [--ntsc]`
adds 42 file-service checks per mode. It pauses in the audited real application
loader, borrows six instruction bytes for a disposable F$SRqMem request, restores
those bytes, and uses the resulting BIOS-allocated 64 KB block for all remaining
code and data. It does not assume the 220 probe's fixed scratch address is free.
Four whole-file payloads, size/EOF/seek/re-read behavior, buffer guards, close and
invalid handles are checked. File hashes are independently compared with the
disc audit. This tool does not export firmware, application code or file contents.

Run `tools/validate_490.py --bios <490-ROM> --dvc <IMPEG-ROM> --disc <Third-Degree-disc>
--output <directory>` after building `bios_contract`, `bios_io_contract`,
`bios_490_contract` and `disc_data_audit`. It records 36 CRC, 32 pointer and 84 file
checks, eight whole-file hash comparisons and before/after input-image hashes.
It also runs `bios_490_contract --buffers` in each mode: two linked PCLs receive
consecutive Form 2 video payloads, independently compared with raw disc sectors.
The probe checks completion flags, byte counts, surrounding buffer guards,
end of the CIL chain, abort, stable buffers after abort and close. This is a
bounded two-buffer test, not a continuous mixed audio/video streaming test.

The 490/IMPEG game probes cover The 7th Guest NTSC through 9,000 fields, replaying
the last 3,500 fields with pointer movement, and Third Degree PAL through 6,000
fields, replaying the last 2,500. Video, audio and state reserialization match.
The original 13-case regression suite and 181 library/application tests pass.
These results do not establish full-game, optical-drive, asynchronous CIL/PCL or
physical Wiimote compatibility on the 490; its board model remains experimental.

### 490 title-screen investigation

Burn-Cycle exposed a CIAP audio completion error: APTR remained within the
completed buffer, causing the real BIOS to unqueue the pending successor instead
of refilling the freed buffer. Completion now points to the other audio buffer.
The regression `completed_audio_buffer_is_the_one_the_bios_can_refill` follows
the BIOS's APTR threshold across four buffer turnovers and fails with the old
behavior. Burn-Cycle advances with sustained audio in the scripted probe.

Dragon's Lair and Space Ace exposed a second timing defect: the first CPU-fed
ADPCM buffer was reported complete after one sector period, although its coding
requires 2..16 periods. These titles use sound-completion callbacks to pace
screen fades. Starting the completion countdown with the queued buffer's coding
duration resolves the reproduced fade stalls. The new timing regression covers
eight coding combinations and fails with the old one-period initial delay.
Existing turnover tests now advance the full buffer duration before expecting
completion. No game-specific event injection or memory patches are retained.

Fresh 490/IMPEG runs of Burn-Cycle PAL, Dragon's Lair NTSC and Space Ace NTSC
each advance through 11,000 fields using the same two-press reproduction script.
Each replays the final 3,000 fields with matching video, audio and reserialized
state. Space Ace reaches the populated high-score screen; Dragon's Lair plays
MPEG video with audio. These are bounded scripted checks; live and full-game
validation remain pending. Restart titles rather than loading a previously
stalled snapshot, whose missing completion event has already been consumed.

The current library/application total is 185 passing tests, with five existing
optional tests ignored. The 13-case baseline passes. These results must not be
presented as confirmation of complete-game or original-hardware equivalence.

The harness supports private `--state-in`/`--state-out` checkpoints for short
reproductions and repeatable `--peek HEXADDR COUNT` reads (up to 256 bytes).
`CDI_PROBE_DISPLAY=1` adds display-register summaries to `--sample` output.
Checkpoints and instruction/memory dumps can contain proprietary game or BIOS
bytes; keep them local and exclude them from distributable reports/releases.

### Burn-Cycle frontend input follow-up

Live testing confirmed Dragon's Lair/Space Ace continue after Start and The 7th
Guest passes its first room, but Burn-Cycle menu selection still failed. A fresh
menu checkpoint reproduced a distinction between relative and absolute host
input: after the game repositions the BIOS cursor, a zero-delta button report
selects at that repositioned coordinate. Absolute host input activates a menu
panel, matching the 220 comparison. The first GUI input test applied this change
to the shell too and was withdrawn after live boot/input regressions. A full
boot test with the user's NVRAM reproduces failure to hand over within 3,000
fields when all reports are absolute. Restoring relative shell reports launches
the disc with the same data.

Shared `boot::send_shell_pointer` and `boot::send_game_pointer` functions now
keep these paths distinct in the GUI and harness. `--absolute-game-input`
reproduces absolute gameplay input with the established shell Play sequence;
`--absolute-input` also changes shell reports and is only a diagnostic comparison.
The core's relative API is unchanged. Regression tests guard the shell button
report format and assert identical serialized Mono-I slave state for both
frontend routes.

Only the Mono-IV Peacekeeper frontend accepts ordinary mouse/key/pad buttons
and follows the mouse when no Wiimote aim is present. Mono-I retains the
established behavior, including its original Peacekeeper path. A/B mappings
are unchanged. Live confirmation is pending; do not call Burn-Cycle fully fixed.


## Desktop controller baseline and BIOS-separated storage (12 November 2026)

The user confirmed that the physical mouse, dedicated gamepad and Wiimote work independently and together with both 220 and 490 BIOSes. Keep that combined-controls executable as the local controller reference. The subsequent BIOS-options and mouse-shortcuts candidates add UI changes and still require live verification.

The new desktop candidate uses NVRAM/220 and NVRAM/490 for per-disc memory, and Savestates/220 and Savestates/490 for state slots. Existing shared NVRAM is copied only when its size matches the target board (8 KB for 220, 32 KB for 490), without replacing either source or existing destination. Legacy state import runs the existing checksum and full BIOS/disc/DVC identity checks before copying it into the selected BIOS folder. Old saves remain available.

Folder capitalization is prepared at desktop startup with a reversible intermediate rename. BIOS files are never included in the executable or release package. The new Start 220/490 dock buttons boot the selected system with no disc inserted. Escape returns from that system screen to the library.

PC-local clock initialization and wall-clock progression are enabled only by the desktop frontend. Headless runs retain their deterministic clock. Restoring a state keeps its emulated time and resets the frontend elapsed-time anchor. The disc info screen uses original alpha-bearing artwork, navy panels and a floating Play/Back dock. The disc stays stationary before Play and uses real elapsed time while loading or viewing in-game disc info. About reads the package version and build identifier automatically.
